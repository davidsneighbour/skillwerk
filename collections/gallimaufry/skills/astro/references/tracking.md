# Migration tracking

Use only when the repository requires issue-backed tracking or the user requests it. Respect the existing tracker, labels, milestones, and document authority. Availability of GitHub does not by itself authorise creating issues or milestones.

For authorised issue creation, inspect existing issues first and reuse matching work. Group by coherent route or shared-system boundaries rather than creating one issue per page automatically. Include the accepted source, affected paths, parity requirements, acceptance criteria, blockers, evidence, and whether the task is parity, cleanup, or an improvement. Use existing labels; creating new labels requires authorisation.

Inventory, foundation, content parity, visual and behavioural parity, cleanup, and later improvements are useful planning phases. Use milestones only when the project needs them and their creation is authorised. Keep dependencies explicit and avoid a large administrative bootstrap before the first useful migration step.

Keep tasks in one authoritative system. If the project already generates a roadmap or synchronises an inbox, use that workflow when available. Do not create duplicate hand-maintained status files or require an unavailable skill. When an external tracker is unavailable, record the local plan and limitation; stop only if the repository's actual rules make tracker availability a prerequisite.

Record parity progress in the existing route or system inventory and link supporting task records rather than duplicating their contents. Keep implementation complete, parity verified, and deliberately removed as separate states. If reporting a progress total, explain the denominator and distinguish accepted removals from verified migrations.
