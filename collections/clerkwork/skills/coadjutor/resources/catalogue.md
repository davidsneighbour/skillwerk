# Skillwerk capability catalogue

Generated from indexed skill entry points by `node scripts/sync-coadjutor-catalogue.ts`. Descriptions reflect source capabilities, not installation status. Do not edit this file by hand.

## Clerkwork

Collection entry point: foreman; coadjutor handles discovery across collections.

* `accessibility-review`: Implement and review accessible frontend markup and interactions, or investigate keyboard, focus, screen-reader, contrast, and semantic issues. Use for accessibility reviews and frontend changes where accessibility materially affects implementation. Target WCAG 2.2 AA unless the project specifies another target.
* `agent-align`: Create or update repository agent instruction files only when the user asks to onboard Clerkwork, asks for agent alignment, or explicitly names agent-align. Always ask for confirmation before changing files.
* `agent-instructions-audit`: Audit repository agent instructions for bootstrap cost, scope quality, duplication, legacy CLAUDE.md content, and correct separation between AGENTS.md, scoped instructions, task references, skills, and documentation. Audit is non-mutating by default; optimise only when explicitly requested.
* `behaviour-spec`: Create, review, and generate tests from strict Behaviour.spec.md files. Use when a repository contains or needs behaviour specifications for features, components, pages, modules, CLIs, APIs, workflows, or integrations; when asked to review a Behaviour.spec.md file; when generating or updating tests from a behaviour specification; or when validating implementation against specified behaviour.
* `coadjutor`: Find and compare skills across all eight Skillwerk collections, then route an authorised request to the selected skill or collection router. Use for coadjutor, cross-collection capability discovery, or choosing which Skillwerk skill handles a topic.
* `commit`: Write Git commit messages that follow the Conventional Commits specification (v1.0.0) — types, scopes, description, body, and footers — with examples and best practices. Use when creating a commit, drafting or reviewing a commit message, or checking commit history for consistency.
* `cspell-inline`: Apply CSpell in-document directives to source and documentation files. Use automatically when the user asks to ignore or accept a word in CSpell, disable or enable CSpell/spell checking for a line, next line, section, or file-local pattern, change compound-word checking, select a dictionary for one file, or otherwise requests an inline CSpell setting. Prefer the narrowest supported directive and never invent unsupported CSpell rule-ID suppression.
* `dependency-maintenance`: Safely maintain npm dependencies in a single-package repository or npm monorepo. Use when asked to inspect outdated packages, update dependency ranges and lockfiles, assess or fix npm audit findings, check Dependabot alerts and dependency PRs, update compatible package groups, track unresolved vulnerabilities in GitHub issues, and validate, commit, and push a complete maintenance run while preserving unrelated work.
* `dnbhq-configs`: Audit DNBHQ repository configuration and coordinate selected package-specific maintenance workflows.
* `foreman`: Interface to the Clerkwork skill collection. Use `foreman overview` to list all available skills by category, use category or topic requests such as `foreman git` or `foreman project` to narrow the catalogue, or route a concrete request such as `foreman packages` or `foreman cspell` to the matching Clerkwork skill. Foreman routes specialist jobs and applies bundled procedures for repository onboarding, CI diagnosis, pull request workflows, conflict resolution, verification, and maintainability review.
* `issues`: Work with project issues using Patrick's GitHub-first issue workflow. Use when inspecting open issues, selecting what to work on next, working on a specific issue, continuing with the next issue, or working through multiple issues. Recognise natural requests such as "check open issues", "work on issue #123", "work on the next issue", and "continue working on issues".
* `janitor`: Simplify the current project's code, tests, documentation, and configuration through evidence-backed removal and focused refactoring. Use for codebase cleanup, dead-code removal, or reducing unnecessary complexity; use check mode for findings without edits.
* `labels`: Analyse issue text or issue metadata and select or apply labels from Patrick's category:value label taxonomy. Use when creating, triaging, reviewing, updating, or closing issues, or when validating whether an issue's existing labels correctly represent its type, workflow status, resolution, priority, and metadata.
* `manage-node-version-policy`: Audits and updates Node.js and npm version declarations across a repository, synchronises package.json engines with actively supported Node.js releases, adds a weekly lifecycle check, and verifies the repository after changes. Use when asked to update Node versions, fix Node engine constraints, remove EOL Node versions, align GitHub Actions with package.json, or enforce an LTS/current Node policy. Triggers on: 'update Node versions', 'check Node engines', 'fix Node workflow versions', 'Node version policy', 'remove EOL Node', 'execute Node updates'.
* `mcp-setup`: List curated MCP servers, inspect client configuration and connection status, or set up a named server for a selected client and scope. Use for Foreman MCP requests and explicit MCP configuration work.
* `osv-scan`: Scan dependencies for known vulnerabilities with osv-scanner, auto-apply safe non-breaking fixes, file GitHub issues for the rest, and track accepted/fixed/workaround decisions in a committed ledger so repeat runs never re-file the same vulnerability. Use when asked to run an OSV scan, check dependencies for vulnerabilities, triage osv-scanner findings, or decide whether to accept, fix, or work around a reported vulnerability.
* `project-state-report`: Analyse a repository's current state, safely fetch and fast-forward remote updates, report what changed since a supplied date phrase or since the user last worked on the project, include GitHub PR and issue activity, and recommend what to do next. Use when asked for a project state report, project catch-up, what changed since yesterday or last week, what happened since we last worked, update from remote and summarize, or a project-task-triage-style status with remote and GitHub activity.
* `project-task-triage`: Maintains the repository task-tracking system by syncing the local TODO.md scratch pad with GitHub Issues and regenerating the local PROJECT.md dashboard. Use when asked to check project status, update task tracking, sync todos with GitHub, regenerate the project dashboard, or recommend next steps. Triggers on: 'check status', 'project status', 'sync todos', 'update project', 'update roadmap', 'triage tasks', 'what's next', 'next steps'.
* `quality-gate-organisation`: Name repository quality-check commands consistently. Use when deciding npm script names or documenting check, lint, validate, format, test, and audit command conventions.
* `repo`: Inspect GitHub repository details, list repositories by topics, and plan or explicitly apply repository topic changes. Use for repo information and repository classification; GitHub.com only, with early rejection of other hosts.
* `resume-interrupted-work`: Manage a project-root RESUME.md handoff file that blocks new work until previously interrupted or paused work is resolved. Use whenever work starts in a repository, when the user says resume, continue, or carry on, or when previous work may have been interrupted.
* `scratchpad`: Persist a finding from the current conversation as a local scratch note in another repository. Use for requests such as "scratch this to markdownlint-config", "scratch this for markdownlint-config", "/scratchpad into markdownlint-config", "write a scratch file about this in the markdownlint-config repo", or "track this upstream in @dnbhq/markdownlint-config". Applies when scratch, track, or note explicitly means saving a local cross-repository finding for later work.
* `whatsapp`: Read scoped customer conversations and relevant attachments in the dedicated WhatsApp Web browser app, extract actionable work context, and draft replies. Use when WhatsApp customer communication is relevant to a named task or the user requests an inbox check.

## Fettle

Collection entry point: fettle

* `fettle-engineer`: Convert an existing evidence-backed Fettle finding into a specific skill improvement or GitHub issue proposal with affected files, benefits, authority constraints, and regression criteria.
* `fettle-inspect`: Inspect one or more agent skills for structural correctness, clarity, conflicts, dead resources, duplication, portability, and unnecessary context. Use for static skill audits, not runtime behaviour analysis.
* `fettle-observe`: Analyse agent execution events and historical logs to find recurring failures, incorrect skill use, repeated corrections, regressions, and excessive work. Use for runtime evidence, not static construction audits.
* `fettle-prove`: Test whether an agent skill behaves as intended with deterministic fixtures and explicitly labelled variable agent-behaviour scenarios. Use for regression validation and instruction-conflict scenarios.
* `fettle-steward`: Audit the health of agent skill collections, including inventory, ownership, dependencies, overlaps, obsolete skills, shared resources, and cross-collection consistency.
* `fettle`: Interface to the Fettle skill collection. Use `fettle overview` to list the Fettle workflows, route a concrete request such as `fettle inspect <skill>` or `fettle observe` to the matching Fettle skill, or use `fettle release <skill>` to prepare the release of an individual skill with a validated Semantic Versioning proposal. Fettle identifies the job and hands it off; it does not duplicate the target skill's work.

## Gallimaufry

Collection entry point: gallimaufry

* `astro`: Build, review, and refactor Astro components and project architecture, or migrate an existing website to Astro with explicit parity checks. Use for Astro-specific rendering, content collections, routing, component APIs, scripts, and migration planning. Confirm an existing Astro project or an explicit migration target before applying.
* `baseline-modernise`: Scan frontend source for candidates where modern Web Platform features might simplify compatibility workarounds. Use for Baseline-aware HTML, CSS, and browser-script modernisation audits. Produces static candidate reports, records compatibility data provenance, and supports separate manual runtime verification; never automatically removes fallbacks or modifies source.
* `distil`: Extract the useful core from social-media posts, infographics, carousels, screenshots, articles, slides, diagrams, documents, and other rhetorically presented material. Use when the user asks to distil, extract, or analyse a source, asks what it is actually saying, whether popular advice holds up, or whether anything useful sits underneath marketing or engagement bait. For requests to create a framework or to dive deep into a source, use interrogate-source instead. Not a summarisation skill.
* `dnb-reference`: Add or update a strict references front matter entry on an AI asset file from a supplied HTTP or HTTPS URL. Use when the user provides a URL and a prompt, skill, instruction, workflow, template, or doc file that should cite that resource in YAML front matter.
* `explain`: Explain a topic, code, document, or error at a requested age, knowledge level, or audience perspective. Use for ELI5, "explain like a 6-year-old", beginner explanations, and explanations for a named audience. A request merely to message someone does not trigger this skill.
* `gallimaufry`: Route Gallimaufry requests to skills for audience-aware explanations, Astro development, frontend modernisation, source analysis, reference frontmatter, and SCQA message rewrites.
* `interrogate-source`: Rigorously interrogate externally sourced material such as screenshots, images, posts, prompts, lists, frameworks, carousels, diagrams, and pasted content. Use when asked to create or build a framework from a source, to dive deep into it, to interrogate it, or to derive reusable knowledge from it. Separates faithful source transcription from critical analysis and reusable knowledge extraction. For requests to distil, extract, or analyse a source, use distil instead.
* `scqa-rewrite`: Rewrite a text using Situation, Complication, Question, and Answer (SCQA). Use when the user wants clearer context, reasoning, and a request or conclusion while preserving the original meaning and tone.

## Idiolect

Collection entry point: No collection router; idiolect handles personal writing profiles, checks, and rewrites directly.

* `idiolect-process`: Rewrite user-facing prose into Patrick's established personal voice while preserving meaning, facts, structure, technical accuracy, and intent. This is a cross-cutting finishing skill: prefer running it on any draft, article, report, explanation, documentation prose, proposal, or other publishable/user-authored text produced by another skill when the user asks to "write this up", "write this up as a draft", "create a draft", "draft this", "write this in my words", "write this in my own words", "make this sound like me", or otherwise indicates that the resulting prose should represent their own voice. It may run after another skill rather than replacing that skill.
* `idiolect-voice`: Edit, rewrite, or review prose so it reads in the author's own voice. Use when the user asks to make a blog post, documentation page, letter, essay, note, announcement, or other prose sound like the author; preserve the author's intent while catching generic AI prose, hype, filler, awkward structure, false intimacy, and bad writing tropes.
* `idiolect`: Capture, check, and apply a person's idiolect - their own distinctive vocabulary, rhythm, and habits in writing. Use when the user wants to build a voice profile from writing samples, check whether a draft sounds like them, or rewrite a draft so it reads in their voice.
* `simple-english`: Write or rewrite text in plain, layman-readable English in the spirit of ASD-STE100 Simplified Technical English: short sentences, active voice, simple tenses, one word one meaning, condition before command, every technical term defined at first use, no AI slop. Default mode is Plain. Strict mode applies full STE vocabulary compliance when the user names STE, ASD-STE100, or compliance. Use for documentation, READMEs, runbooks, procedures, error messages, release notes, incident reports, API guides, and explanations for readers outside the field. Also use when the user says "STE", "Simplified Technical English", "ASD-STE100", "plain English", "layman's terms", "explain it simply", "no jargon", "de-slop", "make this readable", "write for non-native readers", or asks for docs that translate well. The same rules govern the reply: answer first, prose only.
